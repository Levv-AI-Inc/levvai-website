# Flow Studio, section 04: UI specification

This section tells you how to build every Flow Studio screen. It covers each region, control, label, option list, default, helper text, empty state, conditional rule, interaction, keyboard behaviour and message. Other sections of this spec cover the data model, the routing engine and the API. This section only names fields where the UI reads or writes them, and it uses the canonical field names from the seed files (`seed/workflows.json`, `seed/catalog.json`, `seed/people-and-authority.json`, `seed/digital-workers.json`, `seed/onboarding-presets.json`, `seed/systems.json`, `seed/sample-records.json`).

The prototype was built up in layers over 35 rounds, and some of its legacy UI is still in the file, hidden. **This document records the final decisions.** When the prototype and this document disagree, follow this document. Section 16 lists every deliberate difference.

---

## 0. Read this first

### 0.1 Scope

**In scope (build this):**

- One product surface: **workflows**. A workflow is the whole process: what starts it, checks, approvals, tasks, documents, system steps, notifications and timing. Approvals are **Approve steps on the workflow canvas**.
- Pages: the Flow Studio page (top bar, flow picker, canvas, Digital Workers rail) and its overlays (step menu, step panel, Test drawer, Nova drawer, Publish dialog, toasts).

**Out of scope (do not build, even though the prototype file contains code for them):**

- An Approvals tab, approval screens, approval "flows", drill-in or zoom into an approval, breadcrumbs (`‹ Back` crumbs), a "Request approval" step, a shared approvals library, "Approval rules ›" in the picker, a Milestone step, an Update record step, a Take back step.
- The ⚙ Settings button and Settings page (people, roles, signing limits, absences, approval groups, approval rules, Needs fixing). These are managed outside Flow Studio. The Settings button, the Settings page and "Approval rules ›" **must not exist in the DOM at all**: do not render them (the prototype renders them and hides them with CSS; do not copy that). Flow Studio only **reads** them: role holders, groups, people, approval rules and connected systems.
- The Chaser Digital Worker in the rail. The Chaser is a built-in block on Approve, Task and Collect & verify panels (section 6.3).
- The "Ask Nova" free-text bar at the bottom of the canvas. It is hidden in v35 and stays off.
- Deleting workflows. Workflows are never deleted, only switched Active or Inactive (section 11). Steps can be deleted from the editable version.
- Runtime screens: running workflows (Pause, Resume, Stop) and the approver inbox. They are specified in `05-runtime.md`. Flow Studio does not link to them in this release. After **Send for approval** (section 10), the second person approves the publish in the approver inbox.

### 0.2 Visual reference

The prototype ships in the package at `reference/flow-studio-v35.html`. Open it in a browser to compare layouts, spacing, colours and behaviour. **Do not copy its code**: it is a single-file vanilla-JS prototype built in patches, and none of its structure should reach the production codebase. Rebuild everything as React components with Tailwind classes. Use the descriptions and copy in this document as the source of truth.

Global functions you can call in the prototype's browser console, to reach any state quickly: `openFlow('wf-wo-sub')`, then `S.sel='RA_A1'; S.drawer='node'; refresh()` opens a step panel, and `S.drawer='test'` or `S.drawer='nova'` with `refresh()` opens those drawers.

### 0.3 Conventions used here

- Text in "double quotes" is **exact user-visible copy**, including its punctuation. Use curly quotes (“ ” ’) exactly as shown.
- `{braces}` mark a dynamic part, for example "Publish “{workflowName}”".
- **Bold** names in step lists refer to controls.
- Option sets with CAPS names (for example `APPROVER_ROLES`) are defined once in section 6.7 and reused.
- "Dropdown" always means the single reusable **SelectMenu** component (section 13). There are **no pills or chips used as inputs anywhere**, and no native `<select>`. Switches remain switches.
- Prototype IDs (`wf-wo-sub`, `RA_A1`) appear only to help you find a state in the reference file.

## 4. Canvas

The canvas shows the workflow running left to right. The straight horizontal line is the main path. Branches sit **above** it. Approve steps, Ifs, checks, tasks and system steps all live on the same canvas.

### 4.1 Layout algorithm

The prototype's algorithm is described here so the result looks the same. You may implement it with ELK or dagre, as long as you keep these rules.

1. **Columns (levels).** Do a topological pass from Start. Each node's level is the longest path from Start to it. End always takes the maximum level.
2. **Rows.** Do a depth-first walk from Start.
   - A node's **last** exit continues on the node's own row. Exits are ordered as stored in `outs[]`. For an If, Otherwise is last. For a check, Passed is last. For Fits plan?, Outside plan is last.
   - The other exits are placed above: exit `i` of `k` goes to row `parentRow − (k − 1 − i)`.
   - If a (level, row) cell is already taken, move up one row until a free cell is found.
   - Rows are negative upwards. The main path is row 0.
3. **Coordinates.** `x = 70 + level × 220 + 88 × (number of distinct If levels to the left of this level)`. The If card is wider (176px), so later columns shift right by 88px for each If before them. `y = 90 + ifPad + (row − minRow) × 176`, where `ifPad = max over If nodes of (26 × (exits − 2) + 8)` (0 if there are no Ifs). Node squares are 88×88.
4. **Canvas size.** `W = max(x) + 260`, `H = max(y) + 220`.
5. **Edges.** Each edge runs from the source's out-port to the target's in-port as a cubic Bézier: `M x1,y1 C x1+dx,y1 x2−dx,y2 x2,y2` with `dx = max(40, (x2 − x1)/2)`.
   - If any node sits strictly between the two levels, within the row span of the two ends, the edge is **blocked** and runs in a lane instead. For If exits the lane is at `y = max(14, min(y1,y2) − 34 − (k − 1 − i) × 8)`. For all other nodes it is at `y = 40`. The edge curves up into the lane, runs horizontally, and curves down into the target.
   - **Improvement to make:** route blocked lanes just above the highest obstructing node, not at the top of the canvas. The prototype's `y = 40` lanes look like long lines across the top (visible in Contractor onboarding and Assignment ending).
6. **Primary exit rule (fix).** For System steps with a Failed exit, and any node whose exits are added later, keep the **normal** exit (Done) on the main row and put the new exit (Failed) above. The prototype puts the last-added exit on the main row, which pushes Done over the top of the canvas.
7. **Merge points.** The step where the paths of an If meet again is the If's stored `mergeAt` (engine §16.2: computed once on load or when the If is inserted, then updated only by the operations listed there; never recomputed from the current outs, D22). This name appears in the If panel ("All paths meet again at “{name}”") and in "Carry on to “{name}”".

### 4.5 Generated steps (boxes that options create)

Some panel options create real steps on the canvas. They are ordinary, selectable nodes (the user can open and edit them), but the panel option that created them owns them: picking another option removes them.

| Created by | Step created | Name | Where it goes |
|---|---|---|---|
| If path → Then: **Ask someone to approve** | Approve (roles/group/person from **Who approves**) | "{Path name}: approval", for example "Path 2: approval" | on that path's line; continues to the merge point |
| If path or Otherwise → Then: **Escalate: someone must decide** | Approve with `escalation: true` (the person must act), approver from **Escalate to** | "{Path name}: escalation", for example "Otherwise: escalation", "No: escalation" | on that path's line; continues to the merge point |
| If path → Then: **Reject it and send it back to the requester** | End, outcome Rejected | "Rejected" (subtitle "Rejected"), drawn with a red `CircleX` | ends that path |
| If path → Then: **Stop the workflow and tell someone** | Notify (Email) to **Who to tell** | "{Path name}: tell them it stopped" | then End |
| DW check → If it flags something: **Escalate** | Approve with `escalation: true`, approver from **Escalate to** | "{DW name without " check"} flagged: escalation", for example "Duplicate & ghost worker flagged: escalation" (seeded as "Duplicate found: escalation") | on the Flagged line, rejoining the Passed target |
| DW check → **Reject** | End, Rejected | "Rejected" | on the Flagged line |
| DW check → **Stop** | Notify (Email) | "Tell them it stopped" | then End |
| Collect & verify → If it fails: **Escalate: someone must decide** | Approve with `escalation: true`, approver from the escalate dropdown | "{Step name} failed: escalation", for example "Background check failed: escalation" | on a new "Failed" exit of the Collect & verify step, rejoining the step's normal next step. The normal exit is labelled "Done" |
| System → If it fails: **Then take a Failed path** | Task, assigned to People Ops, What they do "Fix what failed in {System}, then retry" | "Fix the {System} error" | on a new "Failed" exit, rejoining the Done target. The normal exit is labelled "Done" |
| Fits plan? (when added) | Approve, Cost center owner | "Outside plan" | on the Outside plan exit |

Renaming a path updates its generated step's name live ("{new name}: approval" / ": escalation" / ": tell them it stopped").

**One escalation timer.** Every generated escalation step (If → Escalate, a check's Escalate, Collect & verify → If it fails → Escalate) is an Approve node with `escalation: true`. Its Chaser field "Then escalate to their manager after (hours)" (`sla`, default **48**) is the **only** escalation timer; there is no separate `elseSla`/`flagSla`. The "Escalate after (hours)" field shown in the If path card, the check panel and the Collect & verify panel reads and writes that same `sla` value on the generated step. Both places always show the same number, and changing either one updates the other immediately.

### 6.6 Delete this step

The last element of every step panel except Start (Workflow settings) and End: the delete button "Delete this step".

- **Effect**: the step is removed. Every line that pointed to it now points to the step's continuing exit. For If and Fits plan? that is the last exit (Otherwise / Outside plan); for a check DW it is Passed; for everything else it is the single exit. Steps generated by the deleted step are removed too.
- The drawer closes. Toast: "Step deleted. Lines reconnected".
- No confirmation dialog. The toast has an **Undo** link (required): Undo restores the exact graph from just before the delete (the step, its generated steps, every reconnected line and `mergeAt`) and autosaves it. The link works until the next edit to the workflow or for 10 s, whichever comes first. Picking Undo shows no new toast.
- Deleting is allowed in the editable version of any workflow. On a live workflow this creates unpublished changes. Workflows themselves cannot be deleted.

### 6.8 Condition editor (used by If paths and by Approve → Only needed when)

A condition group is `{ join: 'all' | 'any', rows: Row[] }`. A row is either a condition `{ f, op, v }` or a nested either/or group `{ join, rows }`. Only one level of nesting is allowed.

**Condition row layout (two lines)**:

```
[ Field ▾                                  ] [×]
[ Comparison ▾ ] [ Value …                     ]
```

- Grid: `grid grid-cols-[minmax(0,.9fr)_minmax(0,1.4fr)_auto] gap-x-1.5 gap-y-1.5`.
  - Line 1: the **Field** dropdown spans columns 1–2, and × (`aria-label="Remove rule"`) sits in column 3.
  - Line 2: the **Comparison** dropdown in column 1 and the **Value** control across columns 2–3.
- Consecutive rows are separated by `border-t border-dashed border-slate-200 pt-2`.
- Use this two-line layout in path cards **and** in Only needed when. The prototype uses a cramped single-line grid in Only needed when; see section 16.

**Field dropdown** (single, searchable, grouped). Groups and fields in this order (labels exact; seed `catalog.json` → `FIELDS`):

- Record: Total value, Bill rate per hour, Work country, Business unit, Job family, Engagement type, Client data access, Vendor's digital worker has system access, Regulated role, Non-standard terms, Scope changed, Fields changed, Hours over schedule, Registration required, Manager chose to extend, Urgent start, Cost center, Legal entity, Site, Worker type

- Levv-calculated: Rate vs rate card (%), Rate vs market median (%), Budget left after request, Months engaged after change, Possible duplicate worker, Days until start date, Invoice matches time and work order, Bill rate change (%)
- Custom fields: Security clearance, Project code

**Comparison and value by field type**:

| Type (`t`) | Fields | Comparison options (label ← stored op) | Value control |
|---|---|---|---|
| money | Total value, Bill rate per hour, Budget left after request | "≥" ← `>=`, ">" ← `>`, "<" ← `<`, "≤" ← `<=` | Number input (`aria-label="Value"`) with a "$" prefix adornment. Stores a number. Empty input stores null |
| num | Months engaged after change, Days until start date | the same four | Number input |

| enum | Work country (UK, Canada, US, Germany), Business unit (Technology, Operations, Finance, Marketing), Job family (Cloud, Data, Analytics, Design, Operations), Engagement type (Off-payroll, Payrolled, Fixed fee, Time and materials), Supplier tier (Preferred, Approved, New), Security clearance (None, Basic, Enhanced), Cost center, Legal entity, Site, Worker type | "is" ← `in`, "is not" ← `not_in` | **Multi** dropdown, placeholder "Choose values". Legal entity: "UK entity", "US entity", "Canada entity", "Germany entity". (The prototype shows bare codes and full legal names in conditions but short labels in Applies to; see section 16.)

**Defaults**:

- Changing the field resets the comparison to the first option. The value resets to: enum `[]`, list the first option, bool none, text `""`, number `0`.
- "+ Add a condition" (mini button) adds **Total value ≥ 250000**.
- "+ Add an either/or condition" (link button; tooltip "For example: Technology, and either over $250K or a regulated role") adds an either/or box set to "any one" with two rows: **Total value ≥ 250000** and **Regulated role is yes**.

**Either/or box**:

```
┃ Either/or: [any one ▾] of these                    [×]
┃ (condition row)
┃ (condition row)
┃ [+ Add another option]
```

- Box: `flex flex-col gap-1.5 rounded-lg border border-dashed border-slate-200 border-l-[3px] border-l-cyan-600 bg-slate-50 p-2`.
- Header row (`flex items-center gap-1.5 text-[12.5px]`): "Either/or:", a small inline dropdown with "any one" (`any`) | "all" (`all`), the text "of these", then × at the right (`aria-label="Remove group"`).
- Then its rows, then the mini button "+ Add another option" (adds Total value ≥ 250000 inside the box).
- An either/or box inside a group reads as "(A or B)" in sentences. For example, "Engagement type is Off-payroll and (Total value ≥ $250K or Regulated role is yes)".

**Condition text** (used on the canvas, in Test and in Nova): each row is "{Field label} {comparison label} {value}". - **+ Add a path**: inserts the new path **before** Otherwise. It is named "Path {n}" (n = number of paths after adding), with all, Total value ≥ 100000, Carry on, and goes straight to the **merge point** (never into another path's generated step). It renames "No" to "Otherwise".
- **Delete path**: removes the path and its generated step. Toast: "Path deleted".
- **Guard**: if a change would leave no path that carries on, it is refused, the dropdown snaps back, and the toast says "At least one path has to carry on". This applies to setting Reject or Stop on a path or on Otherwise. Carry on, approve, escalate and custom all count as carrying on.
- Renaming a path updates the canvas card row and the names of its generated steps live.
- A path with no conditions is allowed. Nova reports it (section 9). No inline error.

## 10. Publish dialog

**Publish** opens a modal dialog.

- Scrim: `fixed inset-0 z-40 grid place-items-center bg-slate-950/55 p-4`. Clicking the scrim closes the dialog.
- Dialog: `w-[min(520px,100%)] max-h-[calc(100vh-32px)] overflow-auto rounded-[14px] border border-slate-200 bg-white`, `role="dialog" aria-modal="true"`, labelled by its title. Focus is trapped inside, the first focus lands on the date input (or on Close when sent), and Escape closes the dialog.

### 10.1 Review state

- **Header**: "Publish “{workflow name}”" (`text-[15.5px] font-semibold`) and ×.
- **Body** (`flex flex-col gap-4 p-[18px]`):
  1. Impact sentence (`text-[15px] leading-normal`): "Applies to new runs. **{n}** records in the last 90 days would have started this workflow. Anything already running keeps its current version." Show `{n}` with tabular numerals.
  2. **Must-fix list**: one row per "Fix before publishing" issue except overlaps (overlaps appear as the questions in item 3): `flex items-start gap-2 text-[13px]` with an 18px rose circle containing "×" and the message. Example: "“Approval” doesn’t say who approves yet."
  3. **Overlap questions**: one group box per active workflow on the same record and event whose Applies to overlaps this one **without** either containing the other. **Identical scopes count as an overlap**, including two "Everywhere" workflows on the same record and event:
     - Label: "This overlaps “{other workflow}” on {count} records. Which one should run?"
     - A dropdown (single, placeholder "Choose…") with two options: this workflow's name and the other workflow's name.
     - Choosing one clears the blocker. The choice (which workflow wins wherever both apply, stored as relative priority) is part of the publish request. It **takes effect only when the second person approves** the publish. Until then the currently live behaviour is unchanged.
     - The impact count in item 1 stays as in the prototype (records in the last 90 days whose record and event match and whose values fall inside this workflow's Applies to). It does not subtract records won by the other workflow. Example: "This overlaps “UK Technology work orders” on 2 records. Which one should run?"
  4. **Ready line**, only when there are no must-fix issues and no unanswered overlaps: an emerald "✓" circle with "Ready to send for approval."
  5. "Goes live on": a date input. Default: the workflow's effective date, or today if that date is in the past (the prototype offers past dates; see section 16). Dates in the past are not allowed: show the inline error "Pick today or a later date." and disable Send.
- **Footer** (`flex flex-wrap justify-end gap-2 border-t border-slate-200 px-[18px] py-3`): **Cancel** (secondary; closes the dialog) and **Send for approval** (primary). Send is **disabled** while there is any must-fix issue, an unanswered overlap, or an invalid date.

### 10.2 Sent state

- Body: "Sent for approval. Anyone with the “Approve flow changes” permission can approve it. You can’t approve your own change." The approver is **any user who has the "Approve flow changes" permission, other than the author**. The request goes to all of them, and the first one to act decides. If no user other than the author has that permission, the review state shows the must-fix row "Nobody else can approve flow changes yet. Ask an admin to give someone the “Approve flow changes” permission." and Send for approval is disabled.
- Footer: a single **Close** button. Ignore the prototype's "Approve as Samira (demo)" and its "Sent to Samira Khan" text: **do not build them**. The second person approves in the approver inbox (05-runtime §7).
- After sending: the top-bar status becomes "Waiting for approval" with an amber dot. The canvas stays editable; further edits go into the next draft.
- When the approver approves: status "Live v{n+1}" and toast "Published as v{n+1}, live on {date formatted like “1 Dec 2026”}". The approval normally happens in someone else's inbox, so the author sees this toast **once**, the next time they load that workflow (the server returns `publishedNotice` and sets the request's `authorNotifiedAt`; 01 §5.1, engine §13.5). The **first publish of a never-published draft** (version 0) becomes **"Live v1"** (toast "Published as v1, …"). Any overlap choice made in the dialog takes effect at this moment. Rejection: status returns to the previous value, plus a notification (runtime).

### 10.3 Acceptance examples

- New workflow with an empty Approve step: the must-fix row "“Approval” doesn’t say who approves yet." is shown and Send for approval is disabled.
- Data and AI hires (Draft): "26 records in the last 90 days would have started this workflow…", plus the overlap question. Send is disabled until a choice is made.
- A new workflow on Work order · Submitted with an empty Applies to: "This overlaps “Work order submitted” on 140 records. Which one should run?" (identical "Everywhere" scopes; options "New workflow" and "Work order submitted"). Send is disabled until a choice is made.
- Site access request: "Applies to new runs… Anything already running keeps its current version." with "✓ Ready to send for approval.", a go-live date, and Send for approval enabled.

## 11. Active / Inactive

- Workflows are **never deleted**. The only control is the switch on the Active row of Workflow settings (section 7.1). A Draft has no switch (it reads "Draft" / "Publish it to make it active.").
- Switching **off** sets the status to Inactive immediately. This is a governance action, not a draft edit: it does not need Publish.
  - The row reads "Inactive" + "Nothing new uses this workflow. Anything already running finishes on it. Turn it back on any time."
  - Toast: "“{name}” is inactive. It can’t be deleted, only turned back on".
  - The top bar status becomes "Inactive · v{n}" with a slate dot.
  - The picker row summary is prefixed with "Inactive · ".
  - Extra amber warning line (fine, `TriangleAlert`, `text-amber-700`), shown when the workflow contains Approve or Auto-approve steps **and** no other active workflow on the same record and event has an empty Applies to: "No other active workflow covers every {record lower}, so new {record lower}s that only this one covers won’t start or be approved until one is active. Nothing is approved automatically." Example: "No other active workflow covers every job posting, so new job postings that only this one covers won’t start or be approved until one is active. Nothing is approved automatically."
- Switching **on**: the status returns to Live, and the toast reads "“{name}” is active again".
- In Test, an inactive workflow shows the inactive note (section 8.2).
- Recommended: ask for confirmation before switching off a workflow that has records in progress ("{n} requests are running on this workflow. They’ll finish on it. Switch it off?" with **Switch off** and **Cancel**). This is not in the prototype.

## 12. New workflow (empty state)

"+ New workflow" in the picker footer:

1. Creates a draft:
   - name "New workflow", status Draft, version 0;
   - record and event copied from the current workflow (for example Work order · Submitted); the request is `POST /api/flow-studio/workflows {fromWorkflowId: <current workflow id>}`;
   - Applies to empty, effective date = the first day of the month after (today + 30 days); with the test date 2026-10-20 that is 2026-12-01, owner "Procurement operations";
   - nodes: Start → End (End outcome Completed);
   - "When a request is finally rejected, tell" = [Hiring manager] (`onReject.recipients = ['hm']`). It is stored at creation, so the field already shows Hiring manager when the first Approve step is added.
2. Navigates to it, fits the canvas, selects Start and opens **Workflow settings**.
3. Toast: "New draft. Set when it runs, then press + to add steps".
4. The canvas shows the Start node (title from Runs when, for example "Work order submitted", subtitle "Everywhere") joined to End ("End" / "Completed") by one line with a "+".
5. The top bar shows "New workflow", an amber dot and "Draft". Test lists the sample records for the copied event.
6. **Nova is not always 0.** A new workflow is a catch-all ("Everywhere"). If another active workflow already exists on the same record and event, identical scopes count as an overlap, so Nova starts at **1** with the Fix-before-publishing item "Overlaps with “{other}” on {count} past records (Everywhere and Everywhere). Set which one wins before publishing." and the button **Choose which wins**. For the default case (copied from Work order submitted) that is "Overlaps with “Work order submitted” on 140 past records (Everywhere and Everywhere). Set which one wins before publishing." It counts in every later Nova total. For example, after adding an Approve step with nobody chosen, Nova shows **2** (that issue and the overlap); after choosing Cost center owner it shows **1** (only the overlap, so the Approve box has no "!"). The overlap is not a must-fix row in Publish: it appears there as the question "This overlaps “Work order submitted” on 140 records. Which one should run?". Nova shows 0 only when no other active workflow exists on that record and event.

No separate empty page is needed. A workflow always has at least Start → End.

## 13. SelectMenu: the one searchable dropdown component

Every selection in Flow Studio uses this component: single or multi, short or long list, people, roles, values, options. Switches stay switches. Native `<select>`, radio pills and checkbox chips must not appear.

### 13.1 Anatomy

```
Closed:   [ Hiring manager, Cost center owner +1        ▾ ]
Open:     [ Choose roles                                ▾ ]  ← button (aria-expanded=true)
          ┌──────────────────────────────────────────────┐
          │ Search…                                      │  ← search input (autofocus)
          ├──────────────────────────────────────────────┤
          │ ROLES                                        │  ← group header (not selectable)
          │ ☐ Hiring manager                             │
          │ ☑ Cost center owner              (bold cyan) │  ← selected
          │▌☐ Department head                ← active row │
          │ + Add “Visa letter”                          │  ← addable lists only
          ├──────────────────────────────────────────────┤
          │ 1 selected                            Clear  │  ← footer (multi only)

```

### 13.2 Props (TypeScript)

```ts

  disabled?: boolean;
  invalid?: boolean;               // rose border
  id?: string;
  'aria-label'?: string;
  'aria-labelledby'?: string;      // preferred: the field label's id
  className?: string;
};

export type SingleSelectProps = Base & {
  multiple?: false;
  value: string | null;
  onChange: (value: string) => void;
};

export type MultiSelectProps = Base & {
  multiple: true;
  value: string[];
  onChange: (value: string[]) => void;
  emptySummary?: string;           // footer text when 0 selected; default "None selected"
  maxSummaryItems?: number;        // default 2 → "A, B +3"
  allowAdd?: boolean;              // shows + Add “…” for unknown text

};

export function SelectMenu(props: SingleSelectProps | MultiSelectProps): JSX.Element;
```

### 13.3 Closed button

- Classes: `flex w-full min-h-9 items-center justify-between gap-2 rounded-lg border border-slate-200 bg-slate-50 px-2.5 py-[7px] text-left text-[13px] text-slate-900 hover:border-cyan-600 aria-expanded:border-cyan-600 focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-1 focus-visible:outline-cyan-600`.
- Value text: `flex-1 truncate`. The placeholder is `text-slate-500`.
- Caret: `ChevronDown` 12px `text-slate-500`.
- The full text is also in the `title` attribute, so it is readable when truncated.
- **Value text**:
  - Single: the selected option's label.
  - Multi: the selected labels joined with ", ". With more than 2 selected: the first 2 then " +{n−2}" (for example "Total value, End date +1").
  - Nothing selected: the placeholder.
  - Options whose meaning is "none" ("No one", "No backup", "Levv connection") are **real values**. Show them in normal text, not placeholder style.
- `type="button"`, `aria-haspopup="listbox"`, `aria-expanded`, `aria-controls={listId}`.

### 13.4 Popover

- Rendered in a portal (`position: fixed; z-index: 9999`) so it is never clipped by the drawer or the canvas.
- Style: `flex flex-col overflow-hidden rounded-[10px] border border-slate-200 bg-white text-slate-900 shadow-[0_12px_32px_rgba(15,23,42,.18)]`.
- **Width**: `max(buttonWidth, 240px)`. Left edge = the button's left, clamped so the popover stays 8px inside the viewport.
- **Height**: `min(320px, max(spaceBelow, spaceAbove))`, where `spaceBelow = viewportHeight − buttonBottom − 12` and `spaceAbove = buttonTop − 12`.
- **Placement**: below the button (4px gap) when `spaceBelow ≥ min(220, spaceAbove)`. Otherwise above (4px gap, anchored by its bottom edge).
- **Search input**: `border-0 border-b border-slate-200 bg-transparent px-3 py-[9px] text-[13px] outline-none`, placeholder "Search…", `aria-label="Search"`. It is focused when the popover opens and keeps the caret at the end. It sets `aria-activedescendant` to the active option's id.
- **List**: `overflow-auto p-1`, `role="listbox"`, `aria-multiselectable="true"` for multi.
- **Group header**: `px-2.5 pb-1 pt-2 text-[11px] uppercase tracking-[0.04em] text-slate-500`, `role="presentation"`. A header is hidden when none of its options match the search.
- **Option**: `flex cursor-pointer items-center gap-2 rounded-md px-2.5 py-[7px] text-[13px] leading-tight`, `role="option"`, `aria-selected`.
  - Selected: `font-semibold text-cyan-700`.
  - Active (keyboard or hover): `bg-cyan-50`.
  - Multi-select options start with a 15px checkbox square (`rounded border-[1.5px] border-slate-200`; when selected `bg-cyan-600 border-cyan-600` with a white ✓).
  - Options with an empty value and empty label are hidden.
- **Search** filters options by a case-insensitive substring match on the label. When nothing matches (and no add row is shown), show "No matches" (`px-2.5 py-2.5 text-[13px] text-slate-500`).
- **Add row** (`allowAdd` only): when the trimmed query is not empty and no option label equals it (case-insensitive), the last row is "+ Add “{query}”" in `text-cyan-700`, with a bold "+" in a 15px column, `role="option"`. Picking it calls `onAdd(query)`, clears the query and keeps the popover open, with the new item now selected.
- **Footer** (multi only): `flex items-center justify-between border-t border-slate-200 px-2.5 py-1.5 text-xs text-slate-500`. Left: "{n} selected", or `emptySummary` ("None selected", or "None selected: applies to all" for Applies to). Right: a **Clear** link (`text-cyan-700`) that deselects everything and keeps the popover open.

### 13.5 Behaviour

| Action | Result |
|---|---|
| Click the button | Opens the popover with an empty search, list scrolled to the top, first visible option active. Clicking it again closes it. Opening another SelectMenu closes this one |
| Type in the search | Filters, makes the first visible option active, resets the list scroll |
| ArrowDown / ArrowUp | Moves the active option (clamped at the ends, no wrap) and scrolls it into view (`block: 'nearest'`). Group headers are skipped |
| Enter | Picks the active option (or the add row). The event does not bubble (so Escape/Enter do not reach drawer handlers) |
| Click an option | Picks it |
| Pick in single mode | Calls `onChange`, closes the popover, returns focus to the button |
| Pick in multi mode | Toggles that value and calls `onChange`. The popover **stays open**, keeps the search text, the list scroll position and the active row, so several items can be ticked in a row. This must survive the parent re-rendering (the prototype reopens the popover after each re-render) |
| Escape | Closes and returns focus to the button. Does not bubble (the drawer stays open) |
| Tab | Closes the popover and lets focus move on |
| Click outside | Closes the popover |
| Scroll of any ancestor (drawer body, page) | The popover **stays attached**: it is repositioned under (or above) the button on every scroll frame. If the button scrolls fully out of the viewport, it closes |
| Window resize | Closes the popover |
| The button unmounts (for example the panel changes) | Closes the popover |

**Accessibility**: the button has `aria-haspopup="listbox"`, `aria-expanded` and `aria-controls`. The listbox has `role="listbox"` and `aria-multiselectable` (multi). Options have `role="option"`, `aria-selected` and a unique `id`. The search input has `aria-activedescendant`. The field label is linked with `aria-labelledby`. All colours meet WCAG AA contrast. The popover is announced by the button's expanded state; no live region is needed.

**Size `sm`** (inline in a sentence: "Take this path when [all ▾] of these are true:", "Either/or: [any one ▾] of these", "Asked only if [all of these ▾]"): `inline-block w-auto min-w-20 align-middle` with the button `min-h-[30px] px-2 py-1`.

## 16. Differences from the prototype (decided here)

Build what this document says. In some places the prototype behaves differently:

1. **Removed surfaces**: the Settings button and page, Approvals tab, approval drill-in and breadcrumbs, Request approval step, Approval rules entry in the picker, Milestone, Update record, Take back, the Ask Nova bar, and "Approve as Samira (demo)" are not built.
2. **No pills**: the Test "Try a record" pills become a single-select list. The path chips in Test stay as read-only tags (they are not inputs).
3. **Approve naming**: the kind is "Approve" (step menu, panel title). A new step's default name is "Approval", and until approvers are chosen the canvas box reads "Approval" / "Choose who approves". The prototype shows "Approve" on the canvas but "Approval" in the If panel, Test and Nova.
4. **Approve → group/person** start empty with a placeholder. The prototype silently selects the first group or the first person (Alan Brooks).
5. **"None" options** ("No one", "No backup", "Levv connection") are shown as real values, not grey placeholders.
6. **Identity & right to work**: only one "Checked by". The prototype shows two.
7. **Contract & policies / Required training**: the preset multi-select and What’s required edit the same items. The prototype shows two independent controls for the same list.
8. **Laptop & badge** (Task preset): the Gives block is shown so the equipment given can be edited. The prototype hides it on Tasks.
9. **"Checked by"** lists "Access provisioner (Digital Worker)". The prototype says "Access (Digital Worker)".
10. **System → Done by** lists only Levv connection and helpers that can do system work (Access provisioner, Access sweeper). The prototype lists check DWs, Job posting writer, Invoice match and Start-date guardian.
11. **Wait sentence**: "If the date on the record changes, the wait moves with it." only in date mode. The unit dropdown has no empty label.
12. **Runs when** labels use the generic N for day events. The prototype shows the current workflow's day count in every option.
13. **Approved-event explainer and Nova message** say "Approve step", not "Request approval step" (legacy wording in the prototype).
14. **Starts from explainer** drops "Simulated in this prototype."
15. **Background check** step-menu description: "Criminal, credit and sanctions checks; adverse results go to the people set under “If it fails”" (engine §20 D25), not "…to an approval".
16. **Job posting writer** one-liner: "Turns a plain request into a job posting", not "…into a requisition".
17. **Placing hint** only mentions attaching where it applies (Document collector → Collect & verify, Access provisioner and Access sweeper → System). The prototype tells every DW, including checks, to "click a Collect & verify step to make it the checker".
18. **Step menu** shows "No steps match “{query}”." when search finds nothing. The prototype shows an empty drawer.
19. **"+ Add a step after all branches finish"** toast reads "Added after all branches finish". The prototype reuses "Added after all paths meet".
20. **If → "Steps added on the canvas"** lists the path's steps in path order. The prototype's list is unordered, for example the Assignment ending "Yes" path.
21. **Condition labels** for Cost center and Legal entity match Applies to (code + name; short entity names). Condition rows use the two-line layout everywhere, including Only needed when.
22. **Picker** groups in record-lifecycle order and indents variations. The prototype uses insertion order with no indent.
23. **Layout**: blocked edges route just above the obstruction (not across the top of the canvas), and a System step's Done exit stays on the main line when a Failed path is added.
24. **Test drawer**: the inactive note comes first. The prototype shows the summary first.
25. **Publish**: "Goes live on" can't be in the past (the prototype pre-fills past dates such as 2026-09-01). The toast date is formatted, not ISO.
26. **One escalation timer**: every generated escalation (If, check, Collect & verify fail) is an Approve node with `escalation: true`, and its Chaser value is the only timer (default 48). The "Escalate after (hours)" field on the If path card, check panel and Collect & verify panel edits that value directly. The prototype keeps separate `elseSla`/`flagSla` values next to the step's own Chaser, and Collect & verify escalation creates no step.
27. **Chaser** validates that escalation comes after the reminder (inline error "Escalation has to come after the reminder.") and blocks publishing until it is fixed.
28. **Curly quotes** everywhere, including "What’s required", "How it’s verified", "isn’t", "can’t" (the prototype mixes straight quotes).
29. **Undo on step delete** is required (section 6.6). **Recommended additions** not in the prototype (optional unless a test asserts them; 00 §3 F13): keyboard navigation in the step menu; Ctrl/⌘+wheel zoom; a confirmation before switching off a workflow with running requests; a save-failure toast; a helper needs-setup line.

30. **Settings and "Approval rules ›"** are not rendered at all. The prototype keeps them in the DOM and hides them with CSS.
31. **First publish** of a never-published draft shows "Live v1".
32. **Overlaps at publish**: identical scopes (for example two "Everywhere" workflows on the same record and event) count as an overlap. The overlap choice takes effect only when the second person approves. The impact count is unchanged from the prototype.
33. **Publish approver**: any user with the "Approve flow changes" permission other than the author. No named approver, and no "Approve as Samira (demo)".
34. **Collect & verify → If it fails → Escalate** creates a generated escalation Approve step on a "Failed" exit, like If and check escalations. The prototype only stores a role.
35. **New workflows** store "When a request is finally rejected, tell" = Hiring manager at creation.
